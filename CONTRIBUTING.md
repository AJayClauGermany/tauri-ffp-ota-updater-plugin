# Contributing

## Layout

| Path                   | Purpose                                                      |
| ---------------------- | ------------------------------------------------------------ |
| `src/`                 | Rust plugin crate (`tauri-plugin-ffp-ota-updater`)           |
| `build.rs`             | Declares plugin commands (generates their permissions)       |
| `permissions/`         | Permission definitions (`default.toml` + autogenerated)      |
| `guest-js/`            | TypeScript API wrapper, built to `dist-js/` (tsc + rollup)   |
| `examples/tauri-app`   | Plain HTML/JS app for trying out the plugin; the tutorial    |
| `examples/consent-app` | Two windows, updates the user approves; run end to end in CI |
| `docs/`                | User documentation (see below)                               |

## Prerequisites

- Rust (see `rust-version` in `Cargo.toml`) and Node.js
- [Tauri system dependencies](https://v2.tauri.app/start/prerequisites/)
  (on Debian/Ubuntu: `libwebkit2gtk-4.1-dev`, `build-essential`, `libxdo-dev`,
  `libssl-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev`)

## Development

Build the JS API and check the Rust crate:

```bash
npm install
npm run check   # fast type-check (TypeScript 7 native compiler)
npm run build   # tsc emits ESM + types, rollup derives the CJS build
cargo check
```

The JS API uses TypeScript 7 (the native compiler). It has no JS compiler API
yet, so `@rollup/plugin-typescript` can't be used; `tsc` does the emit instead.

Run the example app:

```bash
cd examples/tauri-app
npm install
npm run dev
```

The example has no `pubkey`, so it starts as it is and `check()` fails with
`emptyPubkey`; the [tutorial](docs/tutorial.md) adds one. `tauri dev` loads
the frontend from disk, so a downloaded bundle is never shown there. To see an
update applied, follow the tutorial, which uses a release build of the
example.

## Adding a command

1. Add the function in `src/commands.rs` and register it in `src/lib.rs`
   (`generate_handler!`).
2. Add its name to `COMMANDS` in `build.rs`.
3. Add `allow-<command>` to `permissions/default.toml`, unless it should be
   opt-in.
4. Expose it in `guest-js/index.ts`.
5. Document it in `docs/reference/api.md` and, if it is granted by default,
   in `docs/reference/configuration.md`.

## Testing

```bash
cargo test                                    # Rust tests (mock Tauri runtime)
cargo clippy --all-targets --all-features -- -D warnings
cargo fmt --all -- --check
npm run check                                 # TypeScript type-check
```

The Rust tests run without a webview. What only a webview shows (pages being
served and reloaded, the Content Security Policy, permissions per window) is
covered by an end-to-end run of `examples/consent-app`, which builds the app
and drives its buttons:

```bash
cd examples/consent-app
npm install
npm run e2e                                   # Linux without a display: xvfb-run -a npm run e2e
```

It takes a few minutes the first time, for the build. CI runs it on Linux,
macOS and Windows (`.github/workflows/e2e.yml`). The script is
`examples/consent-app/e2e.mjs`; it reaches into the app through a small
remote control that is only compiled in for it (`src-tauri/src/e2e.rs`,
feature `e2e`).

## Releasing

1. Set the new version in `Cargo.toml` and `package.json`, and in the install
   commands of the README. They have to be the same version.
2. Merge that to `main`.
3. Tag the merge commit `v<version>` and push the tag:

   ```bash
   git tag v1.0.0
   ```

   ```bash
   git push origin v1.0.0
   ```

`.github/workflows/release.yml` then creates the GitHub release and attaches
the built JavaScript package (`npm pack`). The install commands of the README
point at that tag and that file, so they work once the workflow has finished,
and not before.

The tag can be pushed at any time after the merge, but it has to be on a
commit that contains the release workflow and has the tag's version in both
`Cargo.toml` and `package.json`: the workflow runs from the tagged commit and
fails if the versions differ. Do not move or reuse a tag once it is pushed;
apps pin it. A later release needs a new version first.

## Documentation

The docs follow [Diátaxis](https://diataxis.fr/): each page serves one need,
and content goes where that need is.

| Directory | For a reader who is… | Write it as… |
| --- | --- | --- |
| `docs/tutorial.md` | learning: wants one guaranteed success | a single path with no choices; every step is run, every result is shown |
| `docs/how-to/` | working: has a goal ("publish on GitHub") | steps for that goal, assuming the basics; link out instead of explaining |
| `docs/reference/` | looking something up | complete, dry and structured like the code; no advice |
| `docs/explanation/` | trying to understand why | prose about design, trade-offs and consequences; no steps |

The README is the on-ramp: what the plugin is, the shortest working setup,
and a map of the rest. When a behaviour changes, update the reference first;
how-to pages and the tutorial should only need a change when the steps do.
Commands in the tutorial and the publishing guides are meant to be run as
written, so run them when you touch them.
